# WORKFLOW 生成指导

WORKFLOW 把项目研发活动串成一条可执行主线，重点说明顺序、衔接、验证要求和何时停止，不重复其他文档里的细节规则。

## 调研重点

- 从分支名（`git branch -a`）、最近 merge/PR 历史（`git log --merges`）、CI 配置、贡献指南推断分支模型、评审流程、发布流程，不套用特定平台流程。
- 从 AGENTS、质量文档和脚本确认实现前后必须执行的动作及验证顺序。
- 确认项目对提交、评审、发布或交付的默认终点。
- 识别必须中断确认的情形，例如范围扩大、破坏性操作或无法验证。
- 如果生成 ICAFE，确认它在流程中的真实位置以及 WORKFLOW 是否需要引用它。
- 涉及大量历史或多个配置文件时派子代理调研，只采用验证过的结论，不采用差异或错误分析。

## 生成要求

使用 `templates/workflow.md` 作为结构起点，并按项目实际阶段调整。

- 主线图只展示关键阶段和回退路径，节点名称使用项目真实术语。
- 每个阶段说明输入、动作、完成条件及下一步，避免写成泛化教程。
- 收尾阶段按仓库证据描述，可以是等待用户、提交、发起评审、发布或其他交付方式。
- “何时停下来”只保留会改变授权、范围或结果可信度的条件。
- 必须保留“推进范围声明”标题和明确的默认终点，供 `think` / `worktree` skill 读取。
- 相关文档链接只指向实际存在或本次生成的文件。

## 避免

- 不预设必须绑卡、使用特定评审平台、执行特定 push 命令或自动提交。
- 不重复 ARCHITECTURE 的包边界或 ICAFE 的字段规则。
- 不把代码写完视为完成；必须明确验证和收尾条件。
