# ICAFE 生成指导

ICAFE 记录项目在 iCafe 中长期有效、能够影响 agent 操作的约定。平台现状必须用 `icafe` skill 的 `icafe-cli` 查出来，用之前先读该 skill 的核心约束（`--brief`、中文字段名、space 用 prefixCode）。仓库文件只能提供线索，不能当结论。

## 调研重点

- 先跑 `icafe-cli version` 和 `login status`，确认能用、已登录并记下 `username`。命令不在 PATH 时用 `~/.icafe-cli/bin/icafe-cli`。没登录就提示用户先登录，不要猜操作人。
- 空间从提交历史里找。`git log --pretty=%s -n 100` 里形如 `popo-386 [Story] xxx` 的提交就是绑卡痕迹，Merge 开头的合并提交和 `DevOps-` 这类自动化前缀不算证据。按前缀分组统计，一个仓库可能不止一个空间。
- 一百条里找不到绑卡痕迹就停止推导，问用户空间名；用户也说不清就只生成骨架文件，待确认项留给团队补。
- 找到空间后取样本。每个空间挑最近绑定的 8 到 15 张卡片，要覆盖出现过的全部类型，用 `card get --space <space> --sequence <s1>,<s2> --brief` 一次查完，别一张张查。
- 样本里有 parent 的卡片顺着往上查到根，拿到完整层级链。再用 `space issue-types --space <space>` 确认这些类型现在还存在，历史遗留类型不写进约定，顺手记下各类型的数字 id，后面查必填项要用。
- 迭代计划用 `plan list` 查。取 `status` 为 ACTIVE 且 path 里日期区间覆盖今天的；都覆盖不到就取最新一条并注明查询日期，计划名禁止编造。
- 必填项用 `card required-fields --space <space> --issue-type-id <id>` 查。接口返回空不代表没有：所属计划和负责人一律按必填处理，负责人默认当前操作人。
- 字段习惯从样本的 `properties` 里对齐。估算工时、优先级这类字段，多张一致写固定值，不一致写选取规则，样本里没有的标待确认，不编。样本取值不在必填项返回的 `options` 里时同样标待确认，不要硬映射。
- 更新已有文件先比对：绑卡痕迹里的空间和类型文件都覆盖了，就只补缺口；出现新前缀或新类型，才对这个空间重查一遍。

## 生成要求

使用 `templates/icafe.md` 作为结构起点，逐空间归纳，多个空间的结论分开写，不合并。

- 层级链只记录包含绑定类型的链路。实测到 Task 都挂在 Story 下、Story 挂在 Feature 下，就写 `Epic -> Feature -> Story -> Task`，并把「Task 不直接挂 Feature」这类从数据里看出来的约束写成显式规则。
- 父卡片写法看样本的 parent 统计：都指向同一张父卡片就写明父卡片 ID；有的挂有的孤立，就写挂载规则，说清何时必须挂、何时允许孤立。
- 允许绑定的卡片类型，从提交里的 `[类型]` 标注和卡片实际 `type.name` 一起确认，归纳出的类型必须在 `issue-types` 结果里存在。
- 提交信息格式从提交历史反推，给出真实示例，说清卡片号、类型标注、描述各自的要求，以及一个提交和卡片的对应关系。
- 时间类字段只写推算规则，比如 `计划提测日期 = 建卡日 + 细估工时`；不要从样本日期反推出「都在周五」这类假规律。
- 更新已有文件时保留仍准确的条目，只改有新证据的部分。
- 文件里只留结论和取值规则，不放推导过程和 CLI 调用细节。写入内容里不得出现 token、内网 IP、他人姓名邮箱。

## 什么时候问用户

- 团队内部约定：一提交一卡还是多提交一卡、估算工时的团队标准、状态流转习惯。
- 调研降级时的空间名确认。
- 拿不准的取值集中一批问，不逐条打断。

## 避免

- 不预设 Epic、Feature、Story、Task 的固定层级，层级只来自父卡片实测。
- 不预设工时、优先级、迭代、负责人或自动建卡策略，取值必须有样本或用户确认。
- 不把别的项目沉淀的字段经验（类型专属字段、特定迭代名）搬进来当默认值。
- 不把 iCafe 规则扩展成通用 Git 或评审平台规则。
