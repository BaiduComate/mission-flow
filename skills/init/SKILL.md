初始化或更新本仓库的知识文档，产出后续会话能直接照着执行的指令与参考文件。

## 项目知识组织与命名

项目的知识文档按照以下的结构进行组织

```
~/path/to/project
├── AGENTS.md
└── docs
    ├── icafe.md
    ├── workflow.md
    ├── architecture.md
    └── other docs
```

进行初始化过程时，首先查找是否已有对应的文件，查找时需要忽略大小写，比如 `WORKFLOW.md` 和 `workflow.md` 视为同种功能的文件。新建文件时按顺序推断文件名称：

1. 社区惯例优先。AGENTS.md 是社区约定文件名，固定大写，不适用默认小写
2. 没有惯例的，跟随项目已有风格，比如项目里已有 docs/ARCHITECTURE.md，就沿用大写和目录位置。
3. 既无惯例也无风格可参考时，默认小写：architecture.md、workflow.md、icafe.md

本文后面用 AGENTS / ARCHITECTURE / WORKFLOW / ICAFE 指代这四个文件，实际文件名按本节决定

## 获取初始化范围

向用户确认要生成哪些文件（使用 question 工具）。其中 AGENTS 是必选的导航入口，其余三个是它索引的知识文档。

| 文件         | 是否必选 | 内容                                             | 被谁引用         |
| ------------ | -------- | ------------------------------------------------ | ---------------- |
| AGENTS       | 必选     | 导航入口、常用命令、核心约束、编码规范、文档索引 | 所有后续会话     |
| ARCHITECTURE | 可选     | 系统地图、包边界、依赖方向、运行时流程           | AGENTS           |
| WORKFLOW     | 可选     | 研发流程主线、推进范围声明                       | AGENTS           |
| ICAFE        | 可选     | iCafe 建卡、绑卡、提交约定                       | AGENTS、WORKFLOW |

- 只生成用户勾选的文件。
- 生成多个文件时，AGENTS 的文档索引必须指向实际生成的其他文件，不能指向没生成的文件。
- 如果用户勾选了 WORKFLOW 或 ICAFE 但没有 AGENTS，提醒用户 AGENTS 是入口，建议一并生成或者更新（但不强制）。

## 调研及生成文档

需要跑命令、翻历史或分析大量源码时派子代理执行，让子代理只回报验证过的事实，不报告差异或错误分析。如果读配置和文档后架构仍不清楚，挑少量有代表性的源码文件找真实入口、包边界和执行流，优先读解释系统如何装配的文件，而不是随机叶子文件。

更多的规则需要读取用户勾选文档对应的 reference 和 template，模板中已经内置了一部分规则，比如更新的策略和规则，这部分不要删掉，只需要替换大括号内的内容。同时更新已有文档时保留仍然准确的内容，不为套模板而重写：

| 文件         | 生成指导                     | 输出模板                    |
| ------------ | ---------------------------- | --------------------------- |
| AGENTS       | `references/agents.md`       | `templates/agents.md`       |
| ARCHITECTURE | `references/architecture.md` | `templates/architecture.md` |
| WORKFLOW     | `references/workflow.md`     | `templates/workflow.md`     |
| ICAFE        | `references/icafe.md`        | `templates/icafe.md`        |

### 写作规则

只写这个仓库特有、agent 猜不到的事实：

- 精确的开发命令和快捷方式，尤其是 agent 容易猜错的
- 如何跑单个测试、单个包或聚焦验证步骤
- 重要时的命令顺序，如 `lint`、`typecheck`、`test`
- monorepo 或多包边界、主要目录归属、真实 app/library 入口
- 文件名看不出来的架构要点
- 与语言/框架默认不同的约定
- 工具链非常规行为：生成代码、迁移、codegen、构建产物、特殊 env 加载、dev server、infra 部署流
- 测试非常规前置条件：fixtures、集成测试依赖、snapshot 流程、必需服务、flaky 或昂贵的套件
- setup 要求、环境坑、运维坑
- 已有指令文件里值得保留的约束，以及它的来源引用

排除：

- 通用软件建议
- 长篇教程或穷尽式文件树
- 显而易见的语言约定
- 无法验证的推测
- **猜的内部工具/平台名**：在代码库里找不到确切名字时不要猜，问用户或留空。很多内部工具（评审系统、问题跟踪、CI 平台）的名字和同类开源项目很像但不是同一个。

拿不准就省略。段落和 bullets 都写短。仓库简单就保持文件简单，仓库大就总结少数几个真正改变 agent 工作方式的结构事实。

### 什么时候问用户

只在仓库回答不了某个重要问题时才问。用 question 工具，最多一批。

好问题：

- 未文档化的团队约定
- 分支 / PR / 发布预期
- 已知但没写下来的 setup 或测试前置条件

## 交叉引用校验

所有文件写完后逐项校验：

1. **索引可达性**：AGENTS 文档索引里列出的每个文档都必须真实存在（考虑大小写和目录位置），文件名与实际生成的一致，不能指向本次未生成且项目也不存在的文件。
2. **无断链**：所有文档里的相对链接指向的文件都存在，包括 WORKFLOW 反向引用的 ICAFE。
3. **mermaid 可解析**：ARCHITECTURE 的 mermaid 图结构完整、括号配对、引用关系自洽。

发现问题当场修复，改完重新走一遍这三条。

## 收尾

- 生成的文件数量、命名、位置在回复里列给用户。
- 提示用户检查生成内容，特别是 ICAFE / WORKFLOW 这类需要团队约定的内容。
- 用户勾选的可选文件项目里已有时，说明改动了什么，不重写已验证的内容。
