## 目标

从当前代码库最近一次提交绑定的 iCafe 卡片出发，反推这个仓库实际在用的 iCafe 空间（可能不止一个）、各空间的卡片类型层级和字段填写习惯，沉淀成 `<repo-root>/docs/icafe.md`，让后续研发活动不必反复询问用户。

**严禁声明：**不得向用户声明本阶段的开始、过程和结果，隐式执行即可；也不得向用户展示 `icafe-kno` 这一内部 skill 名称。

## 产物位置

唯一产物是 `<repo-root>/docs/icafe.md`，默认存储在仓库根目录的 `docs/` 文件夹内，`docs` 目录不存在时先新建目录再写入；纳入版本管理，随代码迭代提交到 icode。写入时**禁止**包含个人 token、内网 IP、他人姓名邮箱等敏感信息。

## 数据获取逻辑

两步链式推导：第一步「数据链路」按 ①定位 → ②查详情 → ③归纳 → ④回填 四段依次执行，前一段的输出是后一段的输入；第二步「总结归纳」把第一步的结论汇总为 `icafe.md` 骨架。**只写查得到的结论，查不到的项标注为待确认，禁止编造。**

### 第一步：数据链路（定位 → 查详情 → 归纳 → 回填）

四段链式执行，前一段的输出为后一段的输入；无卡片时终止，后续段落不执行。

#### ① 定位最近一次提交绑定的卡片

- 调用 `icode` skill 获取最近一次提交绑定的 iCafe 卡片，得到 `<space>-<sequence>`；不可用时回退 `git log --pretty=%s -n 50`，取最近一条形如 `<prefix>-<数字>` 开头的提交信息（如 `popo-153 [Story] 提交内容描述`）
- 最近一次未绑时沿历史向前回溯，最多 50 条；仍无则停止并提醒用户本仓库无绑卡痕迹，不猜空间
- 输出：`卡片ID` 列表（如 `popo-153`），作为②的唯一入参；未找到时输出 `无绑卡痕迹`，②③④ 不执行

#### ② 查询卡片详情

- 将①输出的所有卡片按 `<space>` 分组，同一空间内的序列号用逗号拼接，执行 `icafe-cli card get --space <space> --sequence <seq1>,<seq2>,... --brief --show-children`（单次最多 100 个序列号），从返回的 `cards[]` 中保留每张卡片信息
- 有父卡片(parent不为空)时，同样**批量**查询卡片详情，取各自 `type.name` 确认类型层级；需扩大样本时对更早的绑卡提交重复执行①②段，取 5 到 10 张交叉验证
- 输出：每张卡片一份详情快照（`卡片ID`、`类型`、`父卡片`、`负责人`、`属性`），多张汇总为「样本集合」供③归纳、④回填

#### ③ 归纳空间与类型

输入②样本集合，按卡片号前缀 `<space>` 分组，**空间可能多个**，每个空间都要归纳记录，不能只取第一个；不同空间的结论分别记录，不合并。分组内的归纳项（每个空间逐一执行）：
- **iCafe 空间**：每组卡片号前缀即该组的 `<space>`，同时记录空间中文名，便于人读；不处理父卡片所在空间信息
- **绑定类型**：每组的 `type.name` 即本仓库提交实际绑定的卡片类型，例如 `Story` 或 `Task`；同一空间多张样本类型不一致时，取出现频次最高的作为默认绑定类型，其余作为可选类型一并记录
- **卡片层级**：②查到的各级父卡片 `type.name`，据此写出层级链，如 `Epic(56075) -> Feature(54443) -> Story(5007) -> Task(54444)`；**只记录包含绑定卡片类型的层级链**，与绑定类型无关的链路不得纳入避免误导建卡；不同空间的层级链分别记录，不合并
- **父卡片**：记录绑定的父卡片ID，以最近创建卡片绑定的父卡片为最终结论

**校验**（每个空间执行一次）：执行 `icafe-cli space issue-types --space <space>` 确认归纳的类型名确实存在于该空间，避免把历史遗留类型写成约定，查不到时该空间标为待确认；同时记录每个类型的数字 `id`，作为④ `--issue-type-id` 的入参，类型名不能直接当 id 用

③ 的输出（每空间一份，供④查询入参，并作为第二步 icafe.md 骨架）：`空间`（`<space>`＋中文名）、`绑定类型`（默认在前，可选随后）、`层级链`（`类型A(id) -> 类型B(id)`，仅含绑定类型的链路）、`父卡片`（`<space>-<sequence>`）、`类型ID` 映射；校验失败或证据不足的项标「待确认」。

#### ④ 归纳当前迭代计划

每个空间执行一次，默认值取当前最新的迭代计划，基于步骤②总结最近创建卡片的绑定的所属计划：

- 执行 `icafe-cli plan list --space <space>`，取返回 `data[]` 中 `status` 为 `ACTIVE` 的计划；每项含 `id`、`name`、`path`、`parentId`、`status`
- 确定主迭代线：以②样本卡片「所属计划」取值最集中的那条迭代线为主线，其余并行线只记录不作为默认值
- 从主迭代线的子计划中选当前迭代：`name`/`path` 含日期区间（如 `任务引擎08.17~08.30`）时，取区间覆盖当前日期的那条；无日期区间时取排序最末（最新创建）的一条
- 输出：`当前迭代`（`path` 全路径 + `id`）禁止编造计划名

#### ⑤ 查询必填项并回填取值

必填项字段包括：必填项接口必填参数 + 隐含必填项 + 用户习惯字段列表
  - 必填项接口必填参数：`icafe-cli card required-fields --space <space> --issue-type-id <typeid>` 返回的 `data[]` 字段，`displayName` 为字段名，`options[]` 为下拉选项，
  - 隐含必填项：除接口返回的必填项外，**所属计划**、**负责人**默认作为必填项处理（即使接口未返回也需写入必填项列表）
    - 默认值逻辑：
      - **负责人**：默认值取触发人（当前操作人/提交人）
      - **所属计划**：取值来自④的当前迭代
  - 用户习惯字段：总结历史记录卡片，固定填写字段以及参数值，沉淀下来默认回填字段；用户习惯字段不是固定集，随时间不断丰富

- 回填：取值来自②快照的 `属性`（即 `properties[]`），按 `propertyName` 与 `displayName` 对齐，取 `displayValue`
- 取值规则：多张一致→写为固定值约定；不一致→写取值范围 + 选取规则（如优先级按影响面）；为空→标注「样本为空，待确认」，不编造；不在 `options[]` 内→标注「与当前选项不一致，待确认」，不映射；
  - **数字类型字段**：按照实际情况评估，比如预估工时
  - **时间类型字段**：只写取值规则，比如 预估工时 = 当前时间 + 预估工时
  - **人员类类型字段**：人员类字段，取值userName字段值→涉及QA、PM等负责人复制内容即可，其他情况只写取值规则
  - **其他类型字段**：直接复制最新创建卡片的字段参数值即可
- 输出（按预期的3种类型，作为第二步「必填项列表」「必填项取值」结论及 icafe.md「必填项」小节骨架）：`空间/类型`、`字段`（`displayName`）、`可选值`（`options[]`，非下拉记 None）、`取值`（对齐后的 `displayValue` 或规则）；对不齐、为空或超选项的按「待确认」标注，不猜测


### 第二步：总结归纳

汇总为五项结论，作为 `icafe.md` 的内容骨架：

| 结论项     | 来源 |
| ---------- | ----------------------------------------------- |
| iCafe 空间 | ③，样本卡片按前缀分组后的全部空间及中文名 |
| workflow层级 | ③，父子层级关系（父类型查询 + issue-types 校验），只保留包含绑定类型的层级，无关的类型与层级禁止展示 |
| 绑定类型   | ③，解析提交绑定的卡片类型，不设置严禁绑定的卡片类型 |
| 绑卡规则   | ①提交样本 + ③「绑定类型」，仅允许绑定的类型；未绑定的卡片类型不是严谨绑定的类型 |
| 建卡规则   | ②父卡片类型 + 父子挂载关系，按以下逻辑抽象后再写入：①需求卡片类型：「绑定类型」，**是否新建父卡片**——所有样本 `parent` 均指向同一张父卡片时「否」；存在 `parent` 为空或指向不同父卡片时「是」（未绑定必判「是」）；②**父卡片类型**——③按归纳的`卡片层级`推断；③**是否跨空间绑定父卡片**——父子跨空间为「是」，同空间为「否」；④**父卡片ID**——「是否新建父卡片」为「否」时，填写统一绑定的那张父卡片ID；为「是」时留空（无固定父卡片ID）；建卡即通过 parent 指定父卡片，子类型采用父卡绑定的类型 ⑤ **所属计划**取值来自④的当前迭代|
| 必填项列表 | ④ `card required-fields` 返回的 `data[]` 字段 |
| 必填项取值 | ④与样本 `properties[]` 对齐后的实际取值 |
| 父卡片提取 | ③中，父卡片格式为：`<space>-<sequence>`，当父卡片与绑定卡片空间不一致时，标注：跨空间绑定父卡片，无数据依据默认为：「否」 |
| 是否自动拆分任务卡片 | ③中，子卡片是否进行再次拆分，绑定子卡片如果绑定为：是，否则标记为：「否」，无数据依据默认为：「否」 |


### 确认身份与仓库

- 运行 `icafe-cli login status`，读取返回 JSON 的 `username` 字段作为 `<icafe-username>`；命令不在 `PATH` 时使用 `~/.icafe-cli/bin/icafe-cli login status`
- 未登录或没有返回用户名时，要求用户先完成 iCafe 登录，不要猜测
- 用 `git rev-parse --show-toplevel` 取仓库根目录作为 `<repo-root>`
- 读取已存在的 `<repo-root>/docs/icafe.md`，判断是新建还是更新；`docs` 目录不存在时先新建目录

归纳要求：

1. 每条约定写成可执行的祈使句，不写背景叙述,严禁展示依赖指令和处理逻辑
2. 强弱程度用 **必须** / **禁止** / **尽量** 明确标注，避免模糊表达
3. 空小节直接删除，不保留占位内容，严禁用括号解释取值逻辑
4. 证据不足但会影响建卡行为的项，写在文件末尾的「待确认」小节，不要猜测取值，不展示待确认逻辑以及不确定的原因

### 写入 `<repo-root>/docs/icafe.md`

- 写入路径固定为 `<repo-root>/docs/icafe.md`：`docs` 目录不存在时先新建目录再写入，不要写到其他子目录，也不要顺带修改任何本机配置文件
- `icafe.md` 需要进版本管理：写入后提醒用户将 `docs/icafe.md` 提交到 icode（提交信息按「绑定提交」小节格式绑卡），并检查 `.gitignore` 是否误将其排除；**不要**自行执行 `git add` 或提交
